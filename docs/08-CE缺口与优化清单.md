# 08 · 已知限制与后续计划

> 这一篇写清楚：CE 现在能做什么、在哪些地方会退化、接下来准备补什么。
> 每条都对着代码里的真实位置，不写愿望清单。

---

## 一、已知限制

### 守卫覆盖不到"理解错"

接地守卫与数字守卫管的是**编造**（不存在的文件名、前后矛盾的数），
管不了"材料都真、但理解错了"。后者属于模型能力，代码补不上。

### 检索对"短值查询"不擅长

问「端口多少」「某个键是什么值」这类问题，语义检索命中率低——
因为切块按 400 字左右，键值对被埋在大段正文里。
变通：直接用 `[读:配置文件]`。

### 测试脚本依赖环境变量

`tests/` 里几个脚本靠 `CE_TOOL` / `ASTRBOT_PLUGINS` / `CE_WS` 等环境变量定位，
在默认位置之外要手动设，否则会跳过。

### 单文件

`ce/ce_tool.py` 约 2200 行，一个人读得动、改得动，但两人以上并行改容易撞。
拆模块需要先有可靠的测试（正在补），没测试不敢动。

### 没有 metrics

只有 `[HH:MM:SS]` 前缀的日志和 `/health`。没有请求数、平均耗时、
工具调用次数、守卫拦截次数这类可观测指标。

## 二、验证范围

**验证过：**

```
模型      qwen3-9B Q4_K_M（llama.cpp）
上下文    8192，槽数 1
硬件      RTX 2070S 8G / Windows 10
任务      检索、分段读、多步拆解、回滚、接地拦截、并发隔离
数字      关键词搜索 0.1 ms/次；语义 58 ms/次（311 块，建库 4 秒）
         18 KB 文档 → 6 块 → 3381 字成品，约 60 秒
```

**没验证：**

```
其他模型（7B / 14B / 32B / 非 qwen 系列）
其他推理后端（Ollama / vLLM / LM Studio 的真实行为；回退逻辑已写）
Linux / macOS
多卡、上下文 >32K 的并行
真人长期使用
```

## 三、后续计划

```
① 拆模块         config / index / tools / guards / runner / server 六个文件
② metrics        /metrics 暴露请求数、耗时分布、守卫拦截次数
③ 测试夹具       全部改成临时目录，不依赖任何本机路径
④ 更多模型验证    至少把 7B 与 14B 的退化曲线测出来
⑤ 抓取与写文件    [抓:url] 与 [写:path]，带超时/大小上限/白名单
```

---

## 四、边界（不打算做的）

- 不做通用 agent 框架，不接管编排。
- 不自动判断"哪一步错了"：检查点与标红只给线索，回滚由人决定。
- 不承诺意识/情感这类东西。
- 不追多模态。
